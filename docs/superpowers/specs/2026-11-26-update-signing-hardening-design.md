# 업데이트 서명 점검과 보강 설계

- 상태: 방향 확정(GitHub 쪽 잠금 강화만), 구현 보류 (다른 큰 작업이 머지된 뒤 진행)
- 날짜: 2026-11-26
- 계기: 다른 프로젝트 보안 점검에서 "릴리스 zip 이 바뀌면 검증 없이 설치·실행된다"는 지적이
  나왔고, 빠릿도 같은 위험이 있는지 확인했다.

## 결론

빠릿은 **업데이트 파일의 서명 검증을 이미 하고 있다.** 다른 프로젝트에서 지적된 "검증 없이
설치" 문제는 빠릿에 없다. 다만 **서명 키가 GitHub 안에 들어 있어서**, GitHub 계정을 통째로
빼앗기면 공격자가 정식 서명이 붙은 업데이트를 만들 수 있다. 보강할 곳은 여기다.

## 지금 상태 (코드로 확인한 것)

| 항목 | 상태 | 근거 |
|---|---|---|
| 업데이트 파일 서명 | 있음. 릴리스 때 자동으로 서명 | `.github/workflows/fork-release.yml` (`TAURI_SIGNING_PRIVATE_KEY`) |
| 앱 쪽 검증 | 있음. 앱에 들어 있는 공개키와 맞지 않으면 설치 거부 | `src-tauri/tauri.fork.conf.json` `plugins.updater.pubkey`, `src/App.tsx` `downloadAndInstall` |
| 검증 끄는 설정 | 없음 | `dangerousInsecure…` 류 설정 없음 |
| 업데이트 주소 | HTTPS, GitHub 릴리스 한 곳 | `tauri.fork.conf.json` `endpoints` |
| 릴리스 실행 | 사람이 직접 실행, main 에서만, 초안으로 올라가고 공개는 사람이 누름 | `fork-release.yml` `workflow_dispatch`, `Require main` |
| 서명 개인키 보관 | GitHub 저장소 비밀값 + 본인 맥 `~/.tauri/bbarit-fork.key` | `gh secret list` |
| main 브랜치 보호 | 없음 | GitHub API 응답 "Branch not protected" |

## 경우별 위험

| 어떤 경우에 | 무엇이 | 어떻게 되는지 |
|---|---|---|
| 릴리스에 올라간 파일만 바꿔치기한 경우 (릴리스 쓰기 권한만 탈취) | 서명이 맞지 않음 | 앱이 설치를 거부한다. **이미 막혀 있다** |
| GitHub 계정 전체를 빼앗긴 경우 | 공격자가 main 에 코드를 넣고 릴리스를 실행하면 GitHub 이 정식 키로 서명해 준다 | 업데이트를 누른 사용자에게 설치된다. **남은 가장 큰 위험** |
| 릴리스 빌드에 쓰는 외부 도구(`actions/checkout@v5`, `Swatinem/rust-cache@v2`, `dtolnay/rust-toolchain@stable`)가 변조된 경우 | 버전 이름만 지정되어 있어 내용이 바뀌어도 그대로 실행된다 | 변조된 빌드가 정식 서명을 받는다 |
| 릴리스 쓰기 권한을 가진 공격자가 옛 버전 파일을 "새 버전"이라고 올린 경우 | 서명은 파일만 보증하고 버전 번호는 보증하지 않는다 | 이미 고친 문제가 남아 있는 옛 버전으로 되돌려질 수 있다 (확인 필요) |
| 본인 맥의 키 파일이 유출된 경우 | 키에 암호가 걸려 있어 암호까지 알아야 쓸 수 있다 | 암호가 약하면 위 "계정 탈취"와 같은 결과 |

업데이트 밖의 "받아서 실행" 경로도 확인했다. 에이전트 도구(Claude, Codex, Cursor 등)가 없을 때
빠릿은 설치 명령을 **안내만** 하고 자동으로 실행하지 않는다(`src/terminal/cliLaunchCommand.ts`).
사용자가 안내 버튼을 누른 경우에만 그 도구 공식 설치 명령이 실행된다. 이번 범위에서 뺀다.

## 접근 방법

1. **GitHub 쪽 잠금 강화 (권장, 먼저)** — 릴리스 방식은 그대로 둔다.
   - 릴리스 작업을 "release" 환경으로 묶고 서명 키를 그 환경 전용 비밀값으로 옮긴다.
     main 에서만 쓸 수 있게 제한한다.
   - main 브랜치 보호: 강제 push 금지, PR 과 CI 통과 필수.
   - 외부 도구를 버전 이름 대신 고정된 커밋 번호로 지정한다.
   - 계정: 2단계 인증을 패스키/보안키로, 쓰지 않는 토큰 정리.
   - 한계: 계정을 통째로 빼앗기면 이 설정들도 공격자가 풀 수 있다. 시간을 벌고 흔적을 남길 뿐이다.

2. **서명을 본인 맥에서 하기** — 계정 탈취까지 막는 유일한 방법.
   - GitHub 에서 서명 키를 지운다. GitHub 은 빌드만 하고, 본인이 받은 파일을 맥에서 서명해
     서명 파일과 `latest.json` 을 올린 뒤 공개한다. 이 과정을 스크립트 하나로 묶는다.
   - 대가: 릴리스마다 맥에서 한 단계가 더 생긴다. 키 파일과 암호를 잃으면 기존 사용자는
     자동 업데이트를 못 받고 새로 설치해야 하므로 키 백업이 필수다.

3. **지금대로 두기** — 사용자 수가 적은 동안은 받아들일 수 있다는 판단. 권장하지 않는다.
   1번은 릴리스 절차를 바꾸지 않고도 할 수 있기 때문이다.

결정(2026-11-26): **1번만 한다.** 2번은 지금 키를 맥에만 둘 이유가 없어 미룬다. 사용자가
늘거나 외부에 배포하게 되면 다시 검토한다. 그때 먼저 확인할 것: 빌드는 GitHub 에서 그대로
하고 서명만 맥으로 옮기는 방식인데, 서명 키 없이 빌드가 업데이트용 파일 생성 단계에서
멈추는지 확인하고 멈추면 빌드 설정을 고친다. 키 백업도 먼저 해 둔다.

## 1번 작업 범위 (구현 시)

- `.github/workflows/fork-release.yml`: `environment: release` 추가, 외부 도구 커밋 번호 고정.
  `.github/workflows/opensource-ci.yml` 도 같이 고정.
- GitHub 설정(사람이 승인 후 실행): release 환경 생성과 main 제한, 비밀값 이동, main 브랜치 보호.
- 옛 버전 되돌리기 가능 여부를 개발용 앱으로 확인하고, 가능하면 "현재 버전보다 낮은 파일은
  거부" 검사를 앱에 넣는다.
- `CLAUDE.md` 의 릴리스 절차 문단과 `SECURITY.md` 에 키 보관·분실 시 절차를 적는다.

## 하지 않는 것

- Apple 공증(유료 개발자 계정 필요). 지금의 자체 서명 인증서는 그대로 둔다.
- 외부 에이전트 도구 설치 명령의 검증. 각 도구 공식 설치 경로이며 사용자가 직접 누른다.

## 남은 결정

없음. main 브랜치 보호를 켜면 본인도 main 에 바로 push 할 수 없고 PR 을 거쳐야 하는데, 현재
작업 방식이 이미 PR 이라 영향은 작다고 본다.
