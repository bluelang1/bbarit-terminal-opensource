# 협업 AI 타이핑 설계

상태: 설계 2차 (소유자 답변 반영). **구현 보류** — 진행 중인 다른 큰 작업이 머지된 뒤 시작한다.
작성일 2026-11-23.

원래 메모:

> 협업 AI 타이핑 기능 필요. 같은 화면을 보고 같이 타이핑 하기.
> 프롬프트 요청 이력은 오른쪽에 남는데 다만 누가 요청했는지도 같이 남겨야 함.
> 동시 타이핑을 어떻게 조절할지? 타인 타이핑 허용 체크 박스가 입력란 근처에 있으면 좋을 것 같음.

2차에서 소유자가 정한 것:

- 협업 상대는 인터넷 너머의 사람이다.
- 초대는 링크와 토큰을 함께 보여 주고, 그것을 상대에게 전달한다.
- 빠릿이 없는 사람은 웹 페이지로, 빠릿 사용자는 앱에서 직접 연결한다. 앱에서는 새 터미널 메뉴
  맨 아래 "공유 터미널" 을 고르고 링크와 토큰을 넣으면 탭이 열린다.
- 요청 이력은 이미 있는 오른쪽 프롬프트 패널에, 위쪽의 "현재 프로젝트 / 전체" 탭 옆에 넣는다.

3차에서 소유자가 정한 것:

- 터널 주소가 켤 때마다 바뀌는 것은 이번에는 받아들인다. 고정 주소는 나중에 개선한다.
- 공유 터미널 탭은 앱을 다시 켠 뒤에도 남는다 (앱 업데이트 때마다 사라지면 불편하다).

4차에서 소유자가 정한 것:

- 개별 토큰은 그대로 두고, 여러 명이 한 번에 들어오는 **공통 토큰**도 둔다 (집단으로 같이 작업).
- 승인 창은 기본으로 주인만 답한다. 주인이 "선택한 손님" 또는 "모든 손님" 으로 넓힐 수 있고, 그
  선택은 타인 타이핑 허용 체크박스 근처에 둔다.

## 용어

- **주인**: 터미널 탭을 가진 사람. 그 사람의 컴퓨터에서 Claude 가 돈다.
- **손님**: 주인이 초대해서 같은 탭을 보는 다른 사람. 웹 손님(브라우저)과 앱 손님(빠릿) 두 종류.
- **요청**: AI 에이전트에게 보내는 프롬프트 한 건 (여러 줄 가능, 보내기로 확정된 단위).
- **공유**: 주인의 탭 하나를 손님에게 여는 것. 탭 단위로 켜고 끈다.
- **공유 터미널 탭**: 앱 손님 쪽에 열리는 탭. 자기 컴퓨터에서 도는 프로세스가 없고 주인 화면을 보여 준다.

## 왜 하는가

여러 사람이 한 AI 작업을 같이 보면서 번갈아 지시하고 싶다. 지금은 화면 공유를 켜고 한 사람만
칠 수 있고, 누가 무엇을 시켰는지 남지 않는다.

## 목표

- 주인이 탭 하나를 공유하면, 인터넷 너머의 손님이 같은 화면을 실시간으로 본다.
- 손님은 브라우저로도, 빠릿 앱의 "공유 터미널" 탭으로도 들어올 수 있다.
- 손님이 요청을 보낼 수 있고, 그 요청은 주인의 Claude 탭에 입력된다.
- 오른쪽 프롬프트 패널의 새 "공유" 탭에 요청이 시간 순으로 남고, 요청마다 누가 언제 보냈는지가 붙는다.
- 주인이 입력란 근처의 "타인 타이핑 허용" 체크박스로 손님 입력을 켜고 끈다.
- 두 사람이 동시에 보내도 글자가 섞이지 않는다.

## 하지 않는 것 (1차)

- 손님 컴퓨터에서 Claude 를 돌리는 것. 실행은 항상 주인 컴퓨터다.
- 같은 줄을 두 사람이 글자 단위로 동시에 고치는 것.
- 음성·화상, 손님끼리의 채팅, 공유 내용 녹화.
- 셸 탭 공유. 1차는 AI 에이전트 탭만 (셸은 한 줄이 곧 실행이라 위험이 다르다).
- 중앙 서버. 손님은 주인 컴퓨터에 직접 붙는다.

## 실패로 보는 것

- 주인이 허용하지 않았는데 손님이 권한 승인 창에 답하는 것. 허용한 경우에도 주인이 모르게 지나가는 것.
- 이미 지나간 승인 창에 보낸 답이 다음 승인 창에 들어가는 것.
- 주인이 모르는 사이에 공유가 켜져 있는 것, 공유를 꺼도 손님이 계속 보는 것.
- 공유를 켰더니 Web Terminal 처럼 공유와 상관없는 기능까지 인터넷에 열리는 것.
- 두 사람의 글이 한 프롬프트에 섞여 들어가는 것.
- 이력에 남은 이름이 실제 보낸 사람과 다른 것.

## 접근 방식

### 1. 손님이 무엇으로 보는가 — 웹과 앱 둘 다, 접속 규약은 하나

소유자 결정: 웹 손님과 앱 손님을 모두 지원한다. 만드는 방법은 세 가지를 봤다.

1. **접속 규약 하나 + 손님 화면 모듈 하나를 웹과 앱이 같이 쓴다 (채택).** 주인 앱이 공유용
   WebSocket 을 열고, 손님 화면(터미널 표시 + 입력란 + 상태)을 독립 모듈로 한 번 만든다. 웹 손님은
   그 모듈을 담은 페이지를 열고, 앱 손님은 같은 모듈을 "공유 터미널" 탭 안에 띄운다. 두 손님이
   언제나 같은 기능을 갖고, 고칠 곳이 한 군데다.
2. **앱 손님은 기존 터미널 탭 구성요소(`XTerminal.tsx`)를 그대로 쓰고 입력원만 바꾼다.** 단축키와
   모양이 로컬 탭과 완전히 같아진다. 그러나 `XTerminal.tsx` 는 7000줄이 넘고 로컬 프로세스를 전제로
   한 기능(세션 이어가기, 입력 통로, 상태 감지, 미러링)이 얽혀 있어, 원격 탭에서 그것들을 하나씩
   꺼야 한다. 고장 날 곳이 많다.
3. **앱 손님은 탭 안에 웹 손님 페이지를 그대로 끼워 넣는다 (iframe).** 가장 작다. 그러나 탭 이름,
   알림, 오른쪽 패널과 연결할 수 없어 "앱에서 직접 연결" 의 이점이 거의 없다.

1번으로 간다. 2번의 "로컬 탭과 같은 느낌" 은 1번 모듈에 앱의 글꼴·색 설정을 넘겨주는 것으로 맞춘다.

### 2. 동시 타이핑을 어떻게 조절하는가

1. **요청 단위로 보내기 (채택).** 손님은 터미널에 직접 치지 않고, 자기 화면의 입력란에서 요청을
   다 쓴 뒤 보낸다. 주인 앱은 받은 요청을 줄 세워 하나씩 입력 통로(`queueAutoInput`)로 넣는다.
   글자가 섞일 수 없고, "누가 보낸 요청" 이 한 건으로 남는다.
2. **한 번에 한 사람만 치기 (발언권).** 손님도 터미널에 직접 친다. 한 프롬프트를 두 사람이 이어서
   치면 누구 요청인지 정할 수 없고, 손님의 Enter·Esc 가 승인 창에 닿는 것을 따로 막아야 한다.
3. **제한 없음.** 글자가 섞인다. 제외.

1번으로 간다. "같이 치는 느낌" 은 입력 중 표시("○○ 입력 중")로 보완한다. 2번은 써 본 뒤 필요하면
"직접 키 입력" 옵션으로 얹는다.

## 설계

### 초대: 링크와 토큰

주인이 탭 메뉴에서 "이 탭 공유" 를 누르고 손님 이름을 적으면 초대가 하나 만들어진다.

```
초대: 민수
  링크   https://quiet-river-1234.trycloudflare.com/share/7f3a       [복사]
  토큰   bbs_9Kq2…Zx41                                               [복사]
                                              [링크+토큰 한 번에 복사]
  ● 접속 중 (앱)                                              [끊기]
```

- **링크와 토큰을 따로 보여 준다** (소유자 안). 이 방식에 동의하고, 다음을 덧붙인다.
  - 링크와 토큰을 **서로 다른 경로로** 보낼 때만 따로 보여 주는 것이 보안에 도움이 된다 (예: 링크는
    메신저, 토큰은 전화). 같은 채팅에 둘 다 붙여 넣으면 한 줄짜리와 같다. 그래서 강제하지 않고
    "한 번에 복사" 도 둔다. 한 번에 복사한 것은 `링크#token=토큰` 한 줄이다.
  - 토큰은 주소의 `#` 뒤에 붙인다. `#` 뒤는 서버나 Cloudflare 로 전송되지 않는다. Web Terminal 이
    이미 같은 방식이다 (`SettingsPanel.tsx` 4064-4065).
- **토큰 하나 = 사람 한 명 + 탭 하나.** 초대할 때 주인이 적은 이름이 그 토큰의 이름이고, 그 토큰으로
  보낸 요청은 모두 그 이름으로 남는다. 손님이 스스로 적는 이름은 쓰지 않는다 (남의 이름을 적을 수
  있다).
- 주인은 초대별로 끊을 수 있다. 끊으면 그 토큰은 즉시 무효다. "공유 끝내기" 를 누르거나 탭을 닫으면
  그 탭의 토큰이 전부 무효가 된다. **앱을 끄는 것만으로는 토큰이 무효가 되지 않는다** (아래 "앱을
  다시 켠 뒤" 참고).
- 토큰을 넘겨받은 다른 사람이 들어오는 것까지는 막지 못한다. 같은 토큰으로 두 번째 접속이 생기면
  먼저 붙어 있던 연결을 끊고 주인에게 알린다.
- 주인 이름은 설정의 "표시 이름" 을 쓴다 (새 설정 값). 비어 있으면 "주인".

### 공통 토큰 (여러 명이 한 번에)

개별 초대와 별도로, 탭마다 공통 초대를 하나 만들 수 있다. 링크와 토큰 하나를 여러 사람에게 뿌리면
모두 들어온다.

```
공통 초대                                             최대 [10 ▾] 명
  링크   https://quiet-river-1234.trycloudflare.com/share/7f3a       [복사]
  토큰   bbg_T7mP…a0Lk                                               [복사]
  접속 중 4명                              [토큰 새로 만들기] [공통 초대 끄기]
```

개별 토큰과 다른 점:

| | 개별 토큰 | 공통 토큰 |
|---|---|---|
| 한 토큰으로 들어오는 사람 | 한 명 (두 번째 접속이 오면 먼저 연결을 끊음) | 여러 명 동시에 (주인이 정한 최대 인원까지, 기본 10) |
| 이름 | 주인이 초대할 때 정함. 믿을 수 있음 | **손님이 들어올 때 직접 적음. 확인되지 않은 이름** |
| 한 사람만 내보내기 | 그 초대를 끊으면 끝 | 내보낼 수는 있으나 같은 토큰으로 다시 들어올 수 있음. 막으려면 토큰을 새로 만들어 나머지에게 다시 돌려야 함 |

- 공통 토큰으로 들어온 손님은 처음에 이름을 적는다. 이름은 그 공유 안에서 겹칠 수 없고, 주인 이름이나
  개별 초대에 쓰인 이름은 고를 수 없다. 겹치면 "민수 (2)" 처럼 번호가 붙는다.
- 요청 이력과 참가자 목록에서 공통 토큰 손님은 이름 옆에 표시가 붙는다 (예: "민수 ·공통"). 이 표시는
  "이 이름은 본인이 적은 것" 이라는 뜻이다. 이력에 남은 이름을 실제 사람으로 믿어야 하는 자리라면
  개별 토큰을 쓴다.
- 손님 쪽(브라우저 저장소 또는 앱 저장소)에 임의의 손님 번호를 하나 두어, 다시 붙어도 같은 사람으로
  이어지고 이름이 유지된다.
- 주인은 참가자 목록에서 한 명을 내보낼 수 있다. 내보낸 손님 번호는 그 공유가 끝날 때까지 다시 받지
  않는다. 손님 번호는 손님 쪽 저장소를 지우면 바뀌므로 완전한 차단은 아니다. 확실히 막으려면
  [토큰 새로 만들기] 를 쓴다.
- 공통 토큰도 개별 토큰과 같은 때에 무효가 된다 (끄기, 공유 끝내기, 탭 닫기). 주인 앱을 다시 켜면
  개별 초대와 함께 되살아난다.
- 타인 타이핑 허용이 켜져 있으면 공통 토큰 손님도 요청을 보낼 수 있다. 대기 줄은 한 줄이라 사람이
  많아도 요청은 하나씩 들어간다. 한 사람이 줄을 독점하지 못하게, 손님 한 명이 대기 줄에 둘 수 있는
  요청은 3건까지다.

### 인터넷 연결

- 손님은 주인 컴퓨터에 직접 붙어야 하므로 주인 쪽에 Cloudflare 터널이 필요하다. 주인 컴퓨터에
  `cloudflared` 가 있어야 하고, 없으면 "이 탭 공유" 에서 설치 방법을 안내한다. 손님 쪽은 아무것도
  필요 없다.
- **공유 전용 포트를 새로 둔다.** 지금 터널은 포트 19970 을 내보내는데, 그 포트에는 Web Terminal
  (새 셸을 여는 기능)과 파일 열람 API, 비서 게이트웨이가 함께 있다. 공유 때문에 터널을 켜면 그것들도
  인터넷에서 닿는 곳이 된다 (각자 토큰으로 막혀 있기는 하다). 공유는 화면 전송과 요청 수신만 있는
  전용 포트를 쓰고, 터널도 그 포트만 내보낸다.
- 터널 주소는 켤 때마다 바뀐다 (Cloudflare 무료 임시 터널). 소유자가 1차에서 받아들이기로 했다.
  그래서 주인이 앱을 다시 켜면 **새 링크**를 손님에게 다시 보내야 한다. 토큰은 그대로이므로 손님은
  링크만 바꿔 넣으면 된다. 고정 주소는 나중에 개선한다.
- 터널은 공유 중인 탭이 하나라도 있을 때만 켜져 있고, 마지막 공유가 끝나면 끈다.

### 앱 손님: "공유 터미널" 탭

소유자 안(새 터미널 메뉴 맨 아래 → 링크·토큰 입력 → 탭 열림)을 검토한 결과, 그대로 간다.

```
New terminal                      ┌─ 공유 터미널 연결 ─────────────────────┐
  BBARIT Agent                    │ 링크  [ https://…/share/7f3a          ] │
  …                               │ 토큰  [ bbs_9Kq2…                     ] │
  Gajae                           │ 링크+토큰 한 줄을 붙여 넣어도 됩니다      │
  Doc Terminal                    │                       [취소]  [연결]    │
  ─────────────                   └────────────────────────────────────────┘
  공유 터미널…
```

- 링크 칸에 `링크#token=토큰` 한 줄을 붙여 넣으면 토큰 칸이 자동으로 채워진다.
- 연결되면 현재 프로젝트에 탭이 하나 열린다. 이름은 "민수 ← 희성 · Claude" 처럼 주인과 원래 탭
  이름을 보여 주고, 공유 표시 아이콘이 붙는다.
- 탭 안은 손님 화면 모듈이다: 위에 주인 화면(읽기 전용), 아래에 입력란과 보내기, 상태 한 줄.
- **이 탭은 자기 컴퓨터에서 아무것도 실행하지 않는다.** 그래서 로컬 탭에 붙는 기능에서 모두 뺀다:
  프로세스 생성, 터미널 보관(PTY holder), 탭 닫을 때의 프로세스 정리, Claude 세션 이어가기,
  텔레그램 미러링, 에이전트 릴레이(`agent run/send`), git 상태 확인, 마지막 명령 기록,
  `bbarit-ctl term write`. 구현자는 `App.tsx` 에서 터미널 종류를 보는 곳을 전수 확인해야 한다.
- 웹 손님보다 나은 점: 프로젝트 탭 줄 안에 있고, 주인의 Claude 가 끝났거나 승인을 기다릴 때 앱 알림이
  오며, 오른쪽 프롬프트 패널의 "공유" 탭과 이어진다.
- 앱을 다시 켜도 공유 터미널 탭은 남는다 (소유자 결정). 자세한 동작은 아래 "앱을 다시 켠 뒤".
- 접속 방법 메모: 서버의 출처 검사(`agent_gateway.rs` 111-128)는 브라우저 출처가 서버 주소와 같거나
  출처가 없을 때만 통과시킨다. 앱 웹뷰에서 바로 붙으면 출처가 달라 거부된다. Rust 쪽에서 붙어 프런트로
  넘기거나, 공유 포트의 출처 규칙을 따로 정해야 한다.

### 웹 손님

초대 링크를 브라우저로 연다. 주소에 토큰이 없으면 토큰 입력 칸이 먼저 나온다. 그 뒤는 앱 손님과
같은 화면이고, 오른쪽에 요청 이력이 같이 보인다 (웹에는 앱의 프롬프트 패널이 없으므로 페이지에
직접 둔다).

```
┌─ 희성의 Claude 탭 (보기)  ● 작업 중 ─────────┬─ 요청 이력 ──────────┐
│  (주인 화면과 같은 내용, 주인 크기에 맞춰 축소) │ 14:02 희성            │
│                                              │  로그인 API 테스트 …   │
├──────────────────────────────────────────────┤ 14:05 민수 ✓ 전달됨    │
│ [ 요청을 입력하세요…                   ] [보내기] │  에러 메시지는 한국어로 │
│ 주인이 입력을 허용하지 않았습니다 (보기 전용)     │                      │
└──────────────────────────────────────────────┴──────────────────────┘
```

- 화면 크기의 기준은 주인이다. 손님 화면은 주인의 칸 수에 맞춰 줄여서 보여 주고, 손님 창 크기는
  주인 터미널에 영향을 주지 않는다.
- 허용이 꺼져 있으면 입력란이 잠기고 이유가 적힌다.

### 주인 쪽 화면

공유 중인 탭은 터미널 아래에 얇은 협업 막대가 생긴다.

```
│ > _                                                                      │
├──────────────────────────────────────────────────────────────────────────┤
│ ● 공유 중 · 5명 ▾   [✓] 타인 타이핑 허용   승인 응답 [주인만 ▾]   지영 입력 중… │
│                                                  [초대 관리] [공유 끝내기]  │
└──────────────────────────────────────────────────────────────────────────┘

 "5명 ▾" 를 누르면 참가자 목록:              "승인 응답" 을 누르면:
 ┌──────────────────────────────────────┐   ┌────────────────┐
 │ 민수 (앱)          [ ] 승인   [내보내기] │   │ ● 주인만        │
 │ 지영 (웹)          [✓] 승인   [내보내기] │   │ ○ 선택한 손님…  │
 │ 철수 ·공통 (웹)     [ ] 승인   [내보내기] │   │ ○ 모든 손님     │
 └──────────────────────────────────────┘   └────────────────┘
```

- 에이전트 탭에는 별도 입력란이 없고 Claude 의 입력 줄이 화면 맨 아래에 있으므로, 그 바로 아래가
  "입력란 근처" 다.
- **타인 타이핑 허용**은 탭마다 따로이고 기본은 꺼짐이다. 꺼져 있으면 손님은 보기만 한다. 주인이
  바꾸면 손님 화면에 즉시 반영된다.
- 막대 높이는 터미널 크기 계산에 들어가야 한다 (`src/terminal/terminalStripLayout.ts` 를 거친다).
- 공유 중인 탭은 탭 이름 옆에 표시가 붙는다.

### 요청 이력: 프롬프트 패널의 "공유" 탭

오른쪽 프롬프트 패널 위쪽의 탭 줄에 세 번째 탭을 넣는다.

```
› [bbarit-terminal] [전체] [공유]                          ☆
──────────────────────────────────────────────
 14:07  민수   ✕ 거부됨 · 승인 대기 중
  빌드도 돌려줘
 14:06  지영   ⏳ 대기 (1)
  커버리지도 같이 봐줘
 14:05  민수   ✓ 전달됨
  에러 메시지는 한국어로
 14:02  희성 (주인)
  로그인 API 테스트 추가해줘
```

- "공유" 탭은 **시간 순 기록**이다. 요청마다 보낸 사람, 시각, 결과가 붙는다. 같은 글을 두 번 보내면
  두 줄이다.
- 기존 두 탭([프로젝트], [전체])은 그대로 둔다. 그쪽은 같은 글을 한 줄로 합치고 사용 횟수를 세는
  "다시 쓰는 프롬프트 모음" 이라 보낸 사람을 붙일 수 없다. 그래서 저장소를 섞지 않고 따로 둔다.
- 보이는 내용은 지금 보고 있는 탭의 공유 기록이다. 주인에게는 자기가 공유한 탭의 기록, 앱 손님에게는
  들어가 있는 공유 터미널 탭의 기록이다.
- "공유" 탭 버튼은 지금 보고 있는 탭이 공유 중이거나, 공유 터미널 탭이거나, 남은 기록이 있을 때만
  보인다. 공유를 시작하면 패널을 열고 이 탭으로 바꾼다.
- 줄을 누르면: 주인은 그 글을 다시 보낸다 (기존 패널과 같은 동작). 손님은 자기 입력란에 글이 채워진다.
- 저장: 주인 쪽에 탭별로 최근 200건. 공유가 끝나도 남고, 탭을 지우면 같이 지운다. 손님 쪽은 저장하지
  않고 접속할 때 주인에게서 받는다.
- 손님이 보낸 요청은 주인의 프롬프트 모음([프로젝트], [전체])에는 자동으로 들어가지 않는다.

요청 한 건의 모양:

```ts
interface SharedRequest {
  id: string;
  terminalId: string;
  at: number;
  kind: 'prompt' | 'approval';       // approval = 승인 창에 보낸 키
  author: {
    id: string;
    name: string;
    kind: 'host' | 'guest';
    invite?: 'personal' | 'common';   // common 이면 이름은 본인이 적은 것
  };
  via?: 'app' | 'web';
  text: string;                       // approval 이면 키 이름 ("Enter", "Esc", "2")
  status: 'queued' | 'sent' | 'refused';
  refusedReason?: 'not-allowed' | 'blocked' | 'typing' | 'no-writer' | 'cancelled' | 'stale' | 'queue-full';
}
```

입력 통로에는 이미 "어디서 온 입력인가" 가 있어서(`AutoInputSource`), 나중에 텔레그램·스케줄러가
넣은 입력도 같은 기록에 얹을 수 있다. 1차 범위는 주인과 손님이다.

### 요청이 흐르는 길

1. 손님이 보내기를 누른다 → 공유 서버가 토큰으로 손님을 확인한다 → 주인 앱 프런트로 넘긴다.
2. 주인 앱이 확인한다: 그 탭이 공유 중인가, 타인 타이핑 허용이 켜져 있는가. 아니면 거부로 기록한다.
3. 기록에 `대기` 로 올리고, 그 탭의 대기 줄 끝에 넣는다.
4. 차례가 되면 `queueAutoInput(terminalId, text, { source: 'collab', submit: true })` 로 넣는다.
   - 주인이 치는 중이면 조용해질 때까지 기다린다.
   - Claude 가 승인 대기 중이면 요청 글은 **거부**한다. 손님에게 사유를 돌려준다. (승인 창에 답하는
     것은 글이 아니라 응답 단추로 하고, 권한이 있는 손님만 가능하다. 아래 "승인 창에 누가 답하는가".)
   - Claude 가 작업 중이면 그대로 넣는다. Claude Code 가 받아서 다음 차례에 처리한다.
5. 결과(`전달됨` / `거부됨` + 사유)를 기록에 반영하고 모든 참가자에게 알린다.

세부 규칙 (작성자 판단):

- **주인이 오래 치고 있는 경우**: 입력 통로는 20초를 기다린 뒤 `typing` 으로 거부한다
  (`MAX_WAIT_MS`, `inputGate.ts` 11). 손님 요청은 이 거부를 받으면 버리지 않고 대기 줄 맨 앞에 둔 채
  다시 시도한다. 2분이 지나도 못 넣으면 그때 `거부됨(typing)` 으로 끝낸다. 승인 대기(`blocked`)
  거부는 다시 시도하지 않고 바로 끝낸다.
- **대기 줄과 기록은 주인 앱 프런트에 둔다.** 입력 통로가 프런트에 있기 때문이다. 주인 앱 창이
  가려지거나 최소화되면 손님 요청이 늦게 들어갈 수 있고, 1차에서는 이것을 받아들인다.
- `AutoInputSource` 에 `'collab'` 을 추가한다.

주인이 터미널에 직접 친 프롬프트는 `lastCommand` 가 확정하는 시점(Claude 가 작업을 시작했다고
알릴 때)에 기록으로 올라가고, 요청자는 주인이다. 지금 `lastCommand.ts` 는 "값이 바뀌었다" 만
알리므로(`subscribeLastCommands`), 확정 한 건마다 `(terminalId, text)` 를 넘기는 알림을 새로 낸다.
보내기 전에 Esc 로 지운 글은 확정되지 않으므로 남지 않는다.

### 승인 창에 누가 답하는가

Claude 가 권한 승인을 기다릴 때 누가 답할 수 있는지를 주인이 고른다. 승인 한 번이 주인 컴퓨터에서의
명령 실행이므로 기본은 가장 좁다.

| 선택 | 누가 답할 수 있나 |
|---|---|
| **주인만** (기본) | 주인만. 손님 화면에는 "주인의 승인을 기다리는 중" 이 보인다 |
| **선택한 손님** | 주인 + 참가자 목록에서 "승인" 을 켠 손님 |
| **모든 손님** | 주인 + 지금 들어와 있는 모든 손님 (공통 토큰 손님 포함) |

**놓는 자리 (검토 결과)**: 협업 막대에서 "타인 타이핑 허용" 체크박스 바로 오른쪽에 "승인 응답
[주인만 ▾]" 선택 상자를 둔다. 손님별 선택은 막대에 다 펼치면 사람이 늘 때 자리가 없으므로,
"선택한 손님…" 을 고르면 참가자 목록이 열리고 거기서 사람마다 "승인" 을 켠다. 두 가지 이유로 이
자리가 맞다: 두 권한(글 보내기, 승인하기)을 한눈에 같이 보고, 지금 누가 승인할 수 있는지가 막대에
항상 적혀 있다.

- "승인 응답" 은 타인 타이핑 허용이 켜져 있을 때만 바꿀 수 있다. 타이핑 허용을 끄면 손님 승인도
  함께 멈춘다 (선택 값은 기억한다).
- "모든 손님" 을 고를 때 공통 초대가 켜져 있으면 한 번 확인한다: "이름이 확인되지 않은 손님도 내
  컴퓨터의 명령 실행을 승인할 수 있게 됩니다."
- "선택한 손님" 의 사람별 "승인" 은 개별 토큰 손님과 공통 토큰 손님 모두에게 켤 수 있다. 공통 토큰
  손님은 이름 옆 표시로 구분된다.
- 공유를 새로 시작하거나 주인 앱을 다시 켠 뒤 공유를 다시 시작하면 "승인 응답" 은 **주인만** 으로
  돌아간다 (작성자 판단: 넓힌 권한이 잊힌 채 남지 않게).

**손님이 답하는 방법**: 권한이 있는 손님 화면에는 Claude 가 승인을 기다리는 동안에만 입력란 자리에
응답 단추가 나온다.

```
 Claude 가 승인을 기다립니다 (위 화면의 질문을 확인하세요)
 [Enter 확인]  [Esc 취소]  [↑] [↓]  [1] [2] [3]
```

- 손님이 보낼 수 있는 키는 이 단추들뿐이고(Enter, Esc, 위·아래, 숫자 1~9), 승인 대기 상태일 때만
  받는다. 그 외 키와 Ctrl+C 는 어느 선택에서도 손님이 보낼 수 없다.
- 주인 앱은 받은 키를 `queueAutoInput(terminalId, key, { source: 'collab', submit: false, force: true })`
  로 넣는다. 텔레그램의 Enter·Esc 버튼과 같은 길이다.
- **지나간 승인 창에 답이 들어가지 않게 한다.** 주인 앱은 승인 대기 상태에 들어갈 때마다 번호를
  하나 올리고 손님에게 알린다. 손님의 응답에는 자기가 본 번호가 붙고, 주인 앱은 번호가 지금 것과
  다르면 버린다. 주인과 손님, 또는 손님 둘이 거의 동시에 답했을 때 늦은 답이 다음 승인 창에 들어가는
  것을 이렇게 막는다. 같은 승인 창 안에서는 첫 Enter 또는 Esc 가 들어가면 그 번호를 닫는다.
- 손님이 답할 때마다 요청 이력에 한 줄이 남고("지영 · 승인 응답 · Enter") 협업 막대에 잠깐 표시된다.
  주인이 모르게 지나가지 않게 하기 위해서다.
- 화면의 "다시 묻지 않음" 같은 항목을 손님이 고르면 그 뒤로는 승인 창 없이 실행된다. 선택 상자를
  넓힐 때의 안내 글에 이 점을 적는다.

### 화면을 보내는 길

- **지금 구조에는 출력을 여러 곳으로 나눠 보내는 장치가 없다.** 손님에게 보내려면 아래 둘 중 하나를
  새로 만들어야 하고, 2단계는 이 선택을 위한 짧은 시험 구현으로 시작한다.
  - (가) Rust 에서 나누기: 출력이 줄에 들어가는 지점에서 공유 중인 탭만 손님용 방송 채널로 한 벌 더
    보낸다. 주인 앱 창이 가려져도 손님 화면이 갱신된다. 앱 안에서 도는 터미널과 터미널 보관
    프로세스(PTY holder)를 거치는 터미널 두 경로 모두에 넣어야 하고, 보관 프로세스 쪽은 통신 규약을
    넓혀야 할 수도 있다. 그 경우 2단계 크기가 2~3배가 된다.
  - (나) 프런트에서 넘기기: 프런트가 꺼낸 출력을 그대로 공유 서버에 다시 넘긴다. 작다. 그러나 주인
    앱 창이 가려지거나 최소화되면 손님 화면이 늦어진다.
  - 권장: (가)를 먼저 시험하고, 보관 프로세스 규약 변경이 필요하다고 나오면 1차는 (나)로 내고
    "주인 창이 가려지면 늦어질 수 있음" 을 손님 화면에 적는다.
- 손님이 처음 붙거나 다시 붙으면 저장된 출력 사본(`read_pty_output_buffer`, 약 1MB 까지의 최근
  출력)을 먼저 보내고 그 뒤를 잇는다.
- 에이전트 상태, 기록 변경, "입력 중" 표시는 같은 연결로 별도 메시지로 보낸다.

### 공유의 시작과 끝

- 시작: 탭 메뉴 "이 탭 공유" → 손님 이름을 적고 초대를 만든다. 초대는 여러 개 만들 수 있다.
- 끝: "공유 끝내기" 나 탭 닫기는 그 탭의 모든 손님 연결을 끊고 토큰을 무효로 한다.
- 앱 종료는 연결만 끊고 초대는 남긴다. 다시 켜도 공유는 자동으로 다시 켜지지 않고, 주인이
  [공유 다시 시작] 을 눌러야 한다.

### 앱을 다시 켠 뒤 (업데이트 포함)

앱 업데이트가 잦으므로, 어느 쪽이 앱을 다시 켜도 공유 관계가 사라지지 않게 한다.

**손님 앱을 다시 켠 경우** (주인은 계속 공유 중):

- 공유 터미널 탭이 그대로 복구되고, 저장해 둔 링크와 토큰으로 자동으로 다시 붙는다. 손님이 할 일은
  없다.

**주인 앱을 다시 켠 경우**:

- 주인의 탭에는 "공유 일시 중지 · 민수, 지영" 표시와 [공유 다시 시작] 버튼이 뜬다. **자동으로 다시
  켜지지는 않는다.** 주인이 모르는 사이에 공유가 켜져 있는 것을 실패로 보기 때문이다.
- 주인이 다시 시작하면 초대(이름과 토큰)는 예전 그대로 살아나고, 주소만 새로 나온다. 주인은 새
  링크를 손님에게 보낸다.
- 손님의 공유 터미널 탭은 남아 있고 "연결 끊김 · 주인이 공유를 다시 시작하면 새 링크를 받으세요"
  와 링크 입력 칸을 보여 준다. 새 링크를 붙여 넣으면 저장된 토큰으로 바로 붙는다.
- 주인이 탭에 Claude 세션을 이어서 띄우는 것은 기존 동작 그대로다. 공유는 그 탭에 다시 붙는다.

**저장하는 것**:

- 손님 쪽: 탭마다 링크, 토큰, 주인 이름, 원래 탭 이름. 토큰은 설정 파일(`config.json`)이 아니라 앱
  저장소(`~/.config/octo/bbarit.db`)에 둔다. 텔레그램 봇 토큰과 같은 곳이고 **평문**이다. 탭을 닫으면
  지운다.
- 주인 쪽: 탭마다 초대 목록(이름, 토큰의 해시). 토큰 원문은 저장하지 않는다. 그래서 앱을 다시 켠
  뒤에는 초대 관리 화면에서 예전 토큰을 다시 볼 수 없고, 필요하면 그 사람의 초대를 새로 만든다.
- 요청 기록은 주인 쪽에만 저장한다 (앞의 "요청 이력" 참고).

**토큰이 무효가 되는 경우는 세 가지뿐이다**: 주인이 그 초대를 끊음, 주인이 "공유 끝내기" 를 누름,
주인이 그 탭을 닫음.

### 손님이 보게 되는 것에 대한 경고

손님은 주인 화면에 뜨는 것을 전부 본다. 파일 내용, 환경변수, 토큰이 화면에 나오면 그대로 보인다.
공유를 시작할 때 이 점을 한 번 알린다. 비밀 가림은 패턴 기반이라 믿을 수 없으므로 가려 준다고
약속하지 않는다.

## 다른 작업과의 관계

- **구현 보류.** 지금 진행 중인 큰 작업과 같은 파일(`App.tsx`, `XTerminal.tsx`)을 건드리게 되므로
  그 작업이 머지된 뒤 시작한다. 그때 이 문서의 줄 번호 근거는 다시 확인해야 한다.
- 충돌을 줄이기 위해 새 코드는 새 파일에 둔다: 공유 서버(Rust 새 모듈), 손님 화면 모듈, 협업 막대,
  요청 대기 줄과 기록 저장소. 기존 파일에는 연결 지점만 넣는다 (`App.tsx` 메뉴 한 줄과 탭 종류 분기,
  `PromptLibraryPanel.tsx` 탭 하나, `inputGate.ts` 종류 하나, `lastCommand.ts` 알림 하나).
- 텔레그램 설정 복구가 먼저다 (작고, 이미 있는 코드다). 두 작업은 서로 기다리지 않는다.
- 텔레그램 설계의 허용 목록과 이 설계의 초대는 같은 원칙이다: 주인이 등록한 상대만 입력할 수 있다.

## 작업 순서 (각 단계는 따로 머지할 수 있다)

1. **"공유" 기록 탭** (혼자서도 동작): 주인 요청을 시간 순 기록으로, 프롬프트 패널에 탭 추가, 저장.
2. **보기 전용 공유**: 화면 전송 시험 구현 → 공유 전용 포트와 터널 → 초대(링크·토큰) → 손님 화면
   모듈과 웹 페이지 → 주인 협업 막대.
3. **손님 요청**: 손님 입력란, 타인 타이핑 허용 체크박스, 대기 줄, 거부 사유 회신, 입력 중 표시,
   공통 토큰과 참가자 목록.
   3-2. **손님 승인 응답**: 승인 응답 선택 상자, 사람별 승인, 응답 단추, 승인 창 번호 확인.
   (3 을 써 본 뒤 따로 머지한다. 기본이 "주인만" 이라 3 만으로도 쓸 수 있다.)
4. **앱 손님**: 새 터미널 메뉴의 "공유 터미널", 연결 창, 공유 터미널 탭, 프롬프트 패널 연결, 알림.
5. (써 본 뒤 결정) 직접 키 입력 발언권 방식, 셸 탭 공유.
6. (나중에 개선, 소유자 결정) 켤 때마다 바뀌지 않는 고정 주소.

## 검증

- 자동: 요청 대기 줄(순서, 허용 꺼짐 거부, 승인 대기 거부, 주인 입력 중 대기와 2분 한도), 기록 저장과
  200건 제한, 토큰 판정(탭 범위, 끊은 뒤 거부, 두 번째 접속 처리, 앱 재시작 뒤 해시로 다시 인정),
  손님 메시지 종류 제한(키 입력 거부), `링크#token=` 붙여넣기 풀이, 공유 터미널 탭이 로컬 프로세스
  기능을 부르지 않는지, 공유 터미널 탭의 저장과 복구(탭을 닫으면 토큰 삭제). 공통 토큰(최대 인원,
  이름 겹침, 내보낸 손님 재접속 거부, 토큰 새로 만들기 뒤 옛 토큰 거부, 한 사람 대기 3건 제한).
  승인 응답(세 선택별 허용 판정, 타이핑 허용 꺼짐이면 거부, 승인 대기가 아닐 때 거부, 번호가 다른
  늦은 답 버림, 허용 키 외 거부, 공유 다시 시작 시 "주인만" 으로 복귀).
- 실기: 개발 앱에서 탭 공유 → 터널 주소로 다른 브라우저와 다른 컴퓨터의 빠릿에서 접속해 화면이
  같은지, 허용을 켜고 끌 때 손님 입력란이 바뀌는지, 주인이 치는 도중 손님 요청이 섞이지 않는지,
  승인 창에서 손님 요청이 거부되는지, 공유를 끝내면 손님 연결이 끊기는지, 터널이 공유 포트만
  내보내는지(터널 주소로 Web Terminal 이 열리지 않는지). 주인 앱 창이 가려졌을 때 손님 화면 갱신과
  요청 전달이 얼마나 늦어지는지. 손님 앱을 껐다 켜면 자동으로 다시 붙는지, 주인 앱을 껐다 켜면
  공유가 꺼진 채로 뜨고 [공유 다시 시작] 뒤 새 링크만으로 손님이 다시 붙는지. 공통 토큰으로 세 명이
  동시에 들어와 요청이 순서대로 들어가는지. 승인 응답을 "선택한 손님" 으로 두고 권한 있는 손님과
  없는 손님 화면이 다른지, 주인과 손님이 동시에 답했을 때 다음 승인 창이 건드려지지 않는지.
- 앱 손님 확인에는 빠릿이 깔린 두 번째 컴퓨터가 필요하다.

## 정해진 것과 남은 것

- 정해짐: 터널 주소가 켤 때마다 바뀌는 것을 1차에서 받아들인다. 고정 주소는 나중에 개선한다.
- 정해짐: 공유 터미널 탭은 앱 재시작 후에도 남는다. 그 결과 손님 컴퓨터에 토큰이 평문으로 저장된다.
- 작성자 판단 (소유자가 뒤집을 수 있다): 주인 앱을 다시 켜면 공유는 꺼진 채로 뜨고 주인이 눌러야
  다시 시작한다. 초대와 토큰은 그대로 살아난다.
- 정해짐: 개별 토큰과 공통 토큰을 둘 다 둔다.
- 정해짐: 승인 응답은 기본 "주인만" 이고, 주인이 "선택한 손님" / "모든 손님" 으로 넓힐 수 있다.
  선택 상자는 타인 타이핑 허용 체크박스 오른쪽이다.
- 작성자 판단 (소유자가 뒤집을 수 있다): 공통 토큰 최대 인원 기본 10명, 한 사람 대기 요청 3건까지,
  공유를 다시 시작하면 승인 응답은 "주인만" 으로 복귀, "모든 손님" 은 공통 토큰 손님도 포함하되
  확인을 한 번 거침.
- 남은 결정 없음.

## 구현자에게 맡기는 것

- WebSocket 메시지 형식, 출력 묶음 주기, 다시 붙을 때 이어 받는 방법.
- 공유 전용 포트 번호 (기존 19970/19980/19985/19990, 9223/9323 과 겹치지 않게).
- 앱 손님이 Rust 를 거쳐 붙을지, 공유 포트의 출처 규칙을 따로 둘지.
- 손님 화면 모듈의 묶음 방식 (웹 페이지에 넣는 방법), 화면 축소 방식.
- 협업 막대, 연결 창, 기록 줄의 세부 스타일과 단축키.
