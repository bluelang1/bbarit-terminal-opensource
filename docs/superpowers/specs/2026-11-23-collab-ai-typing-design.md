# 협업 AI 타이핑 설계 검토

상태: 검토 초안 (구현 전, 소유자 결정 필요). 작성일 2026-11-23.

이 문서는 아래 메모를 설계로 풀어 본 것이다. 결정이 필요한 곳은 "소유자가 정할 것" 에 모았다.

> 협업 AI 타이핑 기능 필요. 같은 화면을 보고 같이 타이핑 하기.
> 프롬프트 요청 이력은 오른쪽에 남는데 다만 누가 요청했는지도 같이 남겨야 함.
> 동시 타이핑을 어떻게 조절할지? 타인 타이핑 허용 체크 박스가 입력란 근처에 있으면 좋을 것 같음.

## 용어

- **주인**: 터미널 탭을 가진 사람. 그 사람의 컴퓨터에서 Claude 가 돈다.
- **손님**: 주인이 초대해서 같은 탭을 보는 다른 사람.
- **요청**: Claude 같은 AI 에이전트에게 보내는 프롬프트 한 건 (여러 줄 가능, 보내기를 눌러 확정된 단위).
- **공유**: 주인의 탭 하나를 손님에게 여는 것. 탭 단위로 켜고 끈다.

## 왜 하는가

여러 사람이 한 AI 작업을 같이 보면서 번갈아 지시하고 싶다. 지금은 화면 공유를 켜고 한 사람만
칠 수 있고, 누가 무엇을 시켰는지 남지 않는다.

## 목표

- 주인이 탭 하나를 공유하면, 손님이 같은 화면을 실시간으로 본다.
- 손님이 요청을 보낼 수 있고, 그 요청은 주인의 Claude 탭에 입력된다.
- 탭 오른쪽에 요청 이력이 남고, 요청마다 **누가 언제 보냈는지**가 붙는다.
- 주인이 입력란 근처의 "타인 타이핑 허용" 체크박스로 손님 입력을 켜고 끈다.
- 두 사람이 동시에 보내도 글자가 섞이지 않는다.

## 하지 않는 것 (1차)

- 손님 컴퓨터에서 Claude 를 돌리는 것. 실행은 항상 주인 컴퓨터다.
- 같은 줄을 두 사람이 글자 단위로 동시에 고치는 것 (구글 문서 방식).
- 음성·화상, 손님끼리의 채팅.
- 공유 내용 녹화·재생.
- 셸 탭 공유. 1차는 AI 에이전트 탭만 (셸은 명령 한 줄이 곧 실행이라 위험이 다르다).

## 실패로 보는 것

- 손님이 권한 승인 창에 대신 답해서 주인이 모르는 명령이 실행되는 것.
- 주인이 모르는 사이에 공유가 켜져 있는 것, 공유를 꺼도 손님이 계속 보는 것.
- 두 사람의 글이 한 프롬프트에 섞여 들어가는 것.
- 이력에 남은 이름이 실제 보낸 사람과 다른 것.

## 접근 방식

### 1. 손님이 무엇으로 보는가

1. **웹 페이지 손님 (권장).** 주인 앱이 탭 출력을 원격 서버(19970)의 새 WebSocket 으로 내보내고,
   손님은 초대 링크를 브라우저로 연다. 손님은 앱을 깔 필요가 없고 휴대폰에서도 된다. 토큰 인증,
   출처 검사, 비밀번호, Cloudflare 터널이 이미 이 서버에 붙어 있다. 주인 컴퓨터로 들어오는 주소가
   열린다는 점은 Web Terminal·게이트웨이와 같다.
2. **앱 대 앱 (collab 릴레이 확장).** 손님도 BBARIT 앱에서 "원격 탭" 으로 연다. 화면 품질과 단축키가
   가장 좋다. 그러나 collab 은 방 코드만으로 들어오고 `0.0.0.0` 에 열려 있어 인증부터 다시 만들어야
   하고, 손님 쪽 원격 탭이라는 새 탭 종류가 필요하다. 일이 가장 크다.
3. **tmux + SSH.** 앱 밖에서 이미 되는 방식이다. 누가 보냈는지 남길 수 없고, 손님에게 셸 전체를
   주게 된다. 목표와 맞지 않는다.

1번을 고른다. 2번의 "앱 안에서 보기" 는 나중에 손님 페이지를 앱의 웹뷰 탭으로 여는 것으로 대부분
얻을 수 있다.

### 2. 동시 타이핑을 어떻게 조절하는가

1. **요청 단위로 보내기 (권장).** 손님은 터미널에 직접 치지 않고, 자기 화면의 입력란에서 요청을
   다 쓴 뒤 보낸다. 주인 앱은 받은 요청을 줄 세워 하나씩 입력 통로(`queueAutoInput`)로 넣는다.
   글자가 섞일 수 없고, "누가 보낸 요청" 이 자연스럽게 한 건으로 남는다. 주인이 치는 중이면 3초
   조용해질 때까지 기다리는 규칙도 이미 있다.
2. **한 번에 한 사람만 치기 (발언권).** 손님도 터미널에 직접 친다. 첫 키를 누른 사람이 발언권을
   잡고 3초 쉬면 풀린다. "같이 타이핑" 느낌은 가장 가깝다. 그러나 한 프롬프트를 두 사람이 이어서
   치면 누구 요청인지 정할 수 없고, 손님 키가 그대로 들어가므로 Esc·Enter 로 승인 창에 답하는 것을
   따로 막아야 한다.
3. **제한 없음.** 글자가 섞인다. 제외.

1번을 고른다. "같이 치는 느낌" 은 입력 중 표시("○○ 입력 중")와 미리보기로 보완한다. 2번은 1차를
써 본 뒤 필요하면 "직접 키 입력" 옵션으로 얹는다.

## 설계

### 화면: 주인 쪽

공유 중인 탭은 터미널 아래에 얇은 협업 막대가 생기고, 오른쪽에 요청 이력 패널이 열린다.

```
┌─ Claude 탭 ────────────────────────────────┬─ 요청 이력 ───────────────┐
│                                            │ 14:02 나                   │
│  (Claude Code 화면)                        │  로그인 API 테스트 추가해줘 │
│                                            │ 14:05 민수  ✓ 전달됨       │
│                                            │  에러 메시지는 한국어로     │
│                                            │ 14:06 지영  ⏳ 대기 (1)    │
│ > _                                        │  커버리지도 같이 봐줘       │
│                                            │ 14:07 민수  ✕ 거부됨       │
├────────────────────────────────────────────┤  승인 대기 중이라 보내지 않음│
│ ● 공유 중 · 민수, 지영   [✓] 타인 타이핑 허용 │                            │
│ 지영 입력 중…                    [초대] [공유 끝내기] │                     │
└────────────────────────────────────────────┴────────────────────────────┘
```

- **협업 막대**는 공유 중일 때만 보인다. 에이전트 탭에는 별도 입력란이 없고 Claude 의 입력 줄이
  화면 맨 아래에 있으므로, 그 바로 아래가 "입력란 근처" 다. 오른쪽 28px 버튼 줄은 글자가 들어가지
  않아 체크박스 자리로 맞지 않는다.
- **타인 타이핑 허용**은 탭마다 따로이고 기본은 꺼짐이다. 꺼져 있으면 손님은 보기만 한다. 주인이
  바꾸면 손님 화면에 즉시 반영된다.
- 막대 높이는 터미널 크기 계산에 들어가야 한다 (`src/terminal/terminalStripLayout.ts` 를 거친다).

### 화면: 손님 쪽 (웹 페이지)

```
┌─ 희성의 Claude 탭 (보기)  ● 작업 중 ─────────┬─ 요청 이력 ──────────┐
│  (주인 화면과 같은 내용, 주인 크기에 맞춰 축소) │  (주인과 같은 목록)    │
├──────────────────────────────────────────────┤                      │
│ [ 요청을 입력하세요…                   ] [보내기] │                      │
│ 주인이 입력을 허용하지 않았습니다 (보기 전용)     │                      │
└──────────────────────────────────────────────┴──────────────────────┘
```

- 화면 크기의 기준은 주인이다. 손님 화면은 주인의 칸 수에 맞춰 줄여서 보여 주고, 손님 창 크기는
  주인 터미널에 영향을 주지 않는다.
- 허용이 꺼져 있으면 입력란이 잠기고 이유가 적힌다.
- 에이전트 상태(작업 중 / 승인 대기 / 끝남)를 위에 보여 준다.

### 요청이 흐르는 길

1. 손님이 보내기를 누른다 → 원격 서버가 초대 토큰으로 손님을 확인한다 → 주인 앱 프런트로 넘긴다.
2. 주인 앱이 확인한다: 그 탭이 공유 중인가, 타인 타이핑 허용이 켜져 있는가. 아니면 거부로 기록한다.
3. 이력에 `대기` 로 올리고, 그 탭의 대기 줄 끝에 넣는다.
4. 차례가 되면 `queueAutoInput(terminalId, text, { source: 'collab', submit: true })` 로 넣는다.
   - 주인이 치는 중이면 3초 조용해질 때까지 기다린다 (기존 규칙).
   - Claude 가 승인 대기 중이면 **거부**한다 (기존 규칙). 손님에게 사유를 돌려준다.
   - Claude 가 작업 중이면 그대로 넣는다. Claude Code 가 받아서 다음 차례에 처리한다.
5. 결과(`전달됨` / `거부됨` + 사유)를 이력에 반영하고 모든 참가자에게 알린다.

세부 규칙 (작성자 판단):

- **주인이 오래 치고 있는 경우**: 입력 통로는 20초를 기다린 뒤 `typing` 으로 거부한다
  (`MAX_WAIT_MS`, `inputGate.ts` 11). 손님 요청은 이 거부를 받으면 버리지 않고 대기 줄 맨 앞에 둔 채
  다시 시도한다. 2분이 지나도 못 넣으면 그때 `거부됨(typing)` 으로 끝낸다. 승인 대기(`blocked`)
  거부는 다시 시도하지 않고 바로 끝낸다.
- **대기 줄과 이력은 프런트에 둔다.** 입력 통로가 프런트에 있기 때문이다. 주인 앱 창이 가려지거나
  최소화되면 손님 요청이 늦게 들어갈 수 있고, 1차에서는 이것을 받아들인다. 이력에는 대기 시간이
  그대로 보인다.
- `AutoInputSource` 에 `'collab'` 을 추가한다.

주인이 터미널에 직접 친 프롬프트는 `lastCommand` 가 확정하는 시점(Claude 가 작업을 시작했다고
알릴 때)에 이력으로 올라가고, 요청자는 주인이다. 지금 `lastCommand.ts` 는 "값이 바뀌었다" 만
알리므로(`subscribeLastCommands`), 확정 한 건마다 `(terminalId, text)` 를 넘기는 알림을 새로 낸다.
같은 문장을 두 번 보내면 두 건으로 남는다. 보내기 전에 Esc 로 지운 글은 확정되지 않으므로 남지
않는다.

### 승인 창은 주인만 답한다

손님은 요청 글만 보낼 수 있다. Enter·Esc·Ctrl+C 같은 키와 승인 응답은 보낼 수 없다. 1차에서는
바꿀 수 있는 옵션으로도 두지 않는다. 이유: 승인 한 번이 주인 컴퓨터에서의 명령 실행이기 때문이다.

### 요청 이력

요청 한 건의 모양:

```ts
interface PromptRequest {
  id: string;
  terminalId: string;
  at: number;                       // 보낸 시각
  author: { id: string; name: string; kind: 'host' | 'guest' | 'telegram' | 'discord' | 'slack' | 'scheduler' | 'agent' };
  text: string;
  status: 'queued' | 'sent' | 'refused';
  refusedReason?: 'not-allowed' | 'blocked' | 'typing' | 'no-writer' | 'cancelled';
}
```

- 입력 통로에 이미 "어디서 온 입력인가" 가 있다 (`AutoInputSource`). 그래서 손님 요청만이 아니라
  텔레그램·스케줄러·다른 에이전트가 넣은 입력도 같은 이력에 "누가" 와 함께 남길 수 있다. 1차 범위는
  주인과 손님이고, 나머지는 같은 구조에 얹기만 하면 된다.
- 저장: 탭별로 최근 200건, 프로젝트 저장소에 함께 저장한다. 공유하지 않는 탭에서도 주인 요청 이력은
  남는다 (혼자 쓸 때도 쓸모가 있다).
- 패널은 탭 오른쪽에 접었다 펼 수 있다. 공유를 시작하면 자동으로 펼친다.
- 이력 항목을 누르면 글을 복사한다. 다시 보내기는 주인만 가능하다.

### 누가 보냈는지를 믿을 수 있게

앱에 로그인이 없으므로, 이름은 **주인이 초대할 때 정한다**. 주인이 "민수" 라는 이름으로 초대 링크를
만들면 그 링크로 들어온 사람의 요청은 모두 "민수" 로 남는다. 손님이 직접 적는 이름은 쓰지 않는다
(남의 이름을 적을 수 있다).

- 초대 링크는 사람마다 하나, 탭 하나에만 유효하고, 주인이 언제든 끊을 수 있다.
- 주인 이름은 설정의 "표시 이름" 을 쓴다. 비어 있으면 프로젝트의 gh 계정 이름, 그것도 없으면 "나".
- 링크를 넘겨받은 다른 사람이 들어오는 것까지는 막지 못한다. 그래서 같은 초대로 두 번째 접속이
  생기면 주인에게 알린다.

### 화면을 보내는 길

- **지금 구조에는 출력을 여러 곳으로 나눠 보내는 장치가 없다.** 탭 출력은 터미널마다 하나뿐인
  줄(`OutputQueue`, `src-tauri/src/pty_backend.rs` 625-640)에 쌓이고 프런트가 `read()` 로 꺼내 간다.
  손님에게 보내려면 아래 둘 중 하나를 새로 만들어야 하고, 2단계는 이 선택을 위한 짧은 시험
  구현으로 시작한다.
  - (가) Rust 에서 나누기: 출력이 줄에 들어가는 지점에서 공유 중인 탭만 손님용 방송 채널로 한 벌 더
    보낸다. 주인 앱 창이 가려져도 손님 화면이 갱신된다. 앱 안에서 도는 터미널과 터미널 보관
    프로세스(PTY holder)를 거치는 터미널 두 경로 모두에 넣어야 하고, 보관 프로세스 쪽은 통신 규약을
    넓혀야 할 수도 있다. 그 경우 2단계 크기가 2~3배가 된다.
  - (나) 프런트에서 넘기기: 프런트가 꺼낸 출력을 그대로 원격 서버에 다시 넘긴다. 작다. 그러나 주인
    앱 창이 가려지거나 최소화되면 손님 화면이 늦어진다.
  - 권장: (가)를 먼저 시험하고, 보관 프로세스 규약 변경이 필요하다고 나오면 1차는 (나)로 내고
    "주인 창이 가려지면 늦어질 수 있음" 을 손님 화면에 적는다.
- 손님이 처음 붙거나 다시 붙으면 저장된 출력 사본(`read_pty_output_buffer`, 약 1MB 까지의 최근
  출력)을 먼저 보내고 그 뒤를 잇는다. 이 사본은 처음 화면을 채우는 용도일 뿐 실시간 전송은 위의
  새 장치가 맡는다.
- 에이전트 상태와 이력 변경은 같은 연결로 별도 메시지로 보낸다.
- 주소는 Web Terminal 과 같다: 같은 컴퓨터는 로컬 주소, 밖에서는 Cloudflare 터널 주소. 공유를 켤 때
  접속 비밀번호가 없으면 터널 주소는 내주지 않는다.

### 공유의 시작과 끝

- 시작: 탭의 메뉴에서 "이 탭 공유" → 손님 이름을 적고 초대 링크를 만든다.
- 공유 중인 탭은 탭 이름 옆에 표시가 붙는다 (모르고 켜 둔 상태를 없앤다).
- 끝: "공유 끝내기", 탭 닫기, 앱 종료 중 어느 것이든 그 탭의 모든 손님 연결을 끊고 초대를 무효로
  한다. 앱을 다시 켜도 공유는 자동으로 다시 켜지지 않는다.

### 손님이 보게 되는 것에 대한 경고

손님은 주인 화면에 뜨는 것을 전부 본다. 파일 내용, 환경변수, 토큰이 화면에 나오면 그대로 보인다.
공유를 시작할 때 이 점을 한 번 알린다. 비밀 가림은 패턴 기반이라 믿을 수 없으므로 가려 준다고
약속하지 않는다.

## 텔레그램 복구와의 관계

- 두 작업은 서로 기다리지 않는다. 텔레그램 복구가 먼저다 (작고, 이미 있는 코드다).
- 요청 이력이 생기면 텔레그램으로 들어온 명령도 같은 패널에 "텔레그램 · 채팅 이름" 으로 남는다.
- 텔레그램 설계의 허용 목록과 이 설계의 초대는 같은 원칙이다: 주인이 등록한 상대만 입력할 수 있다.

## 작업 순서 (각 단계는 따로 머지할 수 있다)

1. **요청 이력 패널** (혼자 쓸 때도 동작): 주인 요청을 이력으로, 오른쪽 패널, 저장.
   입력 통로가 넣은 자동 입력에 "누가" 를 붙이는 것까지.
2. **보기 전용 공유**: Rust 출력 구독, 원격 서버 WebSocket, 손님 페이지, 초대 링크, 협업 막대.
3. **손님 요청**: 손님 입력란, 타인 타이핑 허용 체크박스, 대기 줄, 거부 사유 회신, 입력 중 표시.
4. (써 본 뒤 결정) 직접 키 입력 발언권 방식, 앱 안에서 보기, 셸 탭 공유.

## 검증

- 자동: 요청 대기 줄(순서, 허용 꺼짐 거부, 승인 대기 거부, 주인 입력 중 대기), 이력 저장과 200건
  제한, 초대 토큰 판정(탭 범위, 끊은 뒤 거부), 손님 메시지 종류 제한(키 입력 거부).
- 실기: 개발 앱에서 탭 공유 → 다른 브라우저로 접속해 화면이 같은지, 허용을 켜고 끌 때 손님 입력란이
  바뀌는지, 주인이 치는 도중 손님 요청이 섞이지 않는지, 승인 창에서 손님 요청이 거부되는지,
  공유를 끝내면 손님 연결이 끊기는지. 주인 앱 창이 가려졌을 때 손님 화면 갱신과 손님 요청 전달이
  얼마나 늦어지는지 (재서 손님 화면 안내 문구를 정한다).

## 소유자가 정할 것

1. **손님이 무엇으로 보는가**: 웹 페이지(권장) / 앱 대 앱.
2. **동시 타이핑 방식**: 요청 단위로 보내기(권장) / 한 번에 한 사람 직접 치기.
3. **협업 상대가 누구인가**: 같은 사무실·같은 네트워크의 동료인지, 인터넷 너머의 사람인지.
   후자면 터널과 비밀번호가 필수가 되고 2단계의 보안 작업이 커진다.
4. **요청 이력 위치**: 이 문서는 탭 오른쪽의 새 패널로 봤다. 다른 화면을 뜻한 것이면 알려 달라.
5. **승인 응답**: 손님은 절대 못 하게 고정(권장) / 주인이 손님별로 허용할 수 있게.

## 구현자에게 맡기는 것

- WebSocket 메시지 형식, 출력 묶음 주기, 다시 붙을 때 이어 받는 방법.
- 손님 페이지를 `web-terminal.html` 과 합칠지 새 파일로 둘지.
- 이력 패널과 협업 막대의 세부 스타일, 단축키.
- 손님 화면 축소 방식 (글자 크기 조정 / 비율 축소).
